#### Propuesta de contrato P2 para R3

Se mantiene `MembersService.tokenFor(memberId)` para el permiso general existente. Para P2 se propone un método separado, `tokenForSinglePayment(memberId, context)`, cuyo contexto identifique como mínimo `spendId`, `receiver` y `debit`. El token P2 debe quedar vinculado al destino y al monto autorizados, consumirse una sola vez de forma atómica y permanecer exclusivamente en el servidor. R2 lo recibirá mediante un adaptador interno `memberToken`, sin exponerlo al cliente. Tras integrar el PR #2, R3 debe conectar ese adaptador con el almacén de miembros. El diseño concreto del contrato, la persistencia y la garantía de consumo atómico corresponden a R3; esta entrada no los implementa ni modifica `/contracts`.

Riesgo de integración: `payShare(memberId, quoteId)` podría necesitar además un identificador de operación para asociar el token P2 con el gasto correcto. R3 debe resolver esa compatibilidad antes de conectar el flujo.

Las guías oficiales describen la solicitud y continuación de grants salientes; la separación P2, la vinculación del token al contexto y el consumo atómico son requisitos propuestos para la aplicación, no funcionalidades verificadas como automáticas del SDK.
